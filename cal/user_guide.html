🛠️ 測站數量查詢網頁 - 系統篩選邏輯書

本文件詳細記載「條件備選庫」內全部 12 項篩選維度 的底層資料對應關係與核心業務邏輯，供系統操作人員交叉比對與稽核時查閱。

🎯 交互過濾池運算核心（組合邏輯）

當您將左側維度卡片拖曳至中間的過濾池時，系統會遵循以下布林代數（Boolean）演算法進行即時運算：

  • 同維度/同池內【或 (OR) 邏輯】： 如果您在同一個維度（例如「縣市選擇」）內同時勾選了「臺北市」與「新北市」，系統會尋找屬於臺北市或新北市的測站。
  • 跨維度/跨卡片【且 (AND) 邏輯】： 如果您在包含池放了「縣市選擇（臺北市）」與「維護廠商（翰昇）」，系統只會篩選出同時符合這兩項條件的交集觀測點。
  • 包含與排除【差集 (NOT) 邏輯】： 系統會先計算出「🟢 包含池」的所有交集結果，再強力扣除「🔴 排除池」中符合的任何站點。

📋 12 大維度底層分類詳細邏輯

📁 所屬單位 unit / main_cat

業務定義： 劃分觀測資料的上游來源權責單位。

對應資料庫邏輯： 對應 JSON 的 mappings.main 架構。

  • 1 署屬站：中央氣象署各科室直接管轄的核心觀測點。
  • 7 外單位雨量站：包含水利署、北市府、農村水保署等外部合作移轉之雨量觀測計。
  • 4 高公局 / 5 西濱：交通部轄下重大國快道路之專專用邊氣象站。
📡 傳輸方式 transport / sub_cat

業務定義： 測站資料回傳至中心端所使用的實體路由通訊媒介。

  • 區域站(無線電)： 使用專屬無線電頻段，透過中繼站層層轉播回傳（常搭配區域站歸屬維度）。
  • 4G行動數據： 裝載商用電信電路，透過行動網路直接點對點封包回傳。
  • 有人站專線： 部分署屬大型有人站（氣象雷達站等）採用固網專線回傳。
🗺️ 地理行政區（縣市選擇 / 鄉鎮選區） city / town

業務定義： 依據國家標準行政邊界進行測站地理劃分。

對應資料庫邏輯： 採用動態二級連動（Cascade）。

  • 當使用者在過濾池選擇「縣市選擇」（如 3 臺北市）時，「鄉鎮選區」的下拉選單會立刻動態連動，只顯示臺北市轄下的 4 北投區、35 大安區、189 文山區等代碼選項，避免無效條件組合。
⏱️ 資料更新頻率（氣象資料 / 雨量資料） weather-freq / rain-freq

業務定義： 規範封包上傳與資料庫寫入的實時週期間隔。

  • 常規站： 預設為每 10 分鐘或每 1 分鐘動態上傳。
  • 邊坡道路站（如高公局系列）： 針對極端氣候防災需求，部分特殊站點具備秒級（如 1 分鐘內）高頻率雨量警示傳輸邏輯。
🔧 維護廠商 vendor

業務定義： 劃分各測站實體硬體合約維護的權責標案廠商。

對應資料庫邏輯： 對應 JSON 的 mappings.vendor 架構。

  • 1 翰昇、2 勤睿、3 達元：負責常規氣象署與道路標案測站巡檢。
  • 4 到 8（如北市府、水利署、十河分署）：屬於外單位自主運維或指特定專管。可以用來稽核特定廠商在特定梅雨季時的通訊妥善率。
🔒 對外提供狀態 public

業務定義： 控管該測站觀測資料是否開放給大眾或供外部 API 介接。

⚠️ 核心強制邏輯：
  • 民航局（機場站）： 基於航空安全法規與特定軍民航專專用通訊協定，所有民航局轄下之機場測站均強制不對外提供。
  • 環境部（空品站）： 資料範疇屬於環境空氣品質指標，非典型大氣要素，依權責限制在流程中預設不對外提供。
📍 測站類型 station_type

業務定義： 定義該實體觀測點上佈署的感測器能力型態。

對應資料庫邏輯： 對應 JSON 的 mappings.station_type 架構。

  • 1 氣象站：同時具備氣溫、氣壓、風向風速等多要素觀測。
  • 2 農業氣象站：額外包含日照、土壤濕度等農業專專用參數。
  • 4 區域站 / 5 雨量站：以觀測降雨量為主，多配置於山區防災熱點。
  • 6 雙中繼站 / 7 單中繼站：無實體觀測感測器，其主要任務為接收盲區自動站訊號，並轉發回地方中心。
🏢 區域站歸屬 regional-center / folder

業務定義： 當傳輸方式為無線電時，中繼站與自動站實體歸屬控管的十三大核心氣象中心。

對應資料庫邏輯： 對應 JSON 的 regionalCenters 經緯度星狀拓撲。

  • 自動站若配置有 repid（代表它將訊號丟給特定中繼站），則會跟隨中繼站的 folder。
  • 全台劃分為：臺北、新竹、梧棲、臺中、日月潭、嘉義、臺南、高雄、恆春、宜蘭、花蓮、臺東等中心。篩選此維度時，系統會自動在背景建立星狀網路，繪製自動站 ➔ 中繼站 ➔ 區域中心的實體通訊連線。
🚀 上架狀態 status

業務定義： 控管測站是否在前台主系統串流中正式發布與展示。

⚠️ 核心強制邏輯（未上架規範）：
  • 教學站（如新北教學站）： 供學術研究、系統內部測試使用，非正式簽收節點，屬於未上架。
  • 備援站（含所有資料後綴為「(備)」之測站）： 如 東引(備)、馬公機場(備)。備援站主要在主站故障時頂替路由，正常情況下，其資料未正式上架前台，避免數據重複累加。
🏔️ 海拔高度 altitude / alt

業務定義： 依據測站實體設置地點的平均海平面以上高度（公尺）進行範圍篩選。

對應資料庫邏輯： 對應 JSON 的數字型態 alt 欄位（例如：玉山站為 3952）。

  • 採用「區間數值交集」演算法。若僅輸入最低值（如 500），系統會撈出所有大於 500 公尺的淺山與高山站；若兩者皆輸入（如 1000 ~ 2000），則可精準鎖定特定中海拔霧林帶的觀測網妥善率。
